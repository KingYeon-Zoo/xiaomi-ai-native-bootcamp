# AI 协作决策记录 — Day2 作业

> 每条记录包含目的、输入、建议、人工判断、验证五个字段。人工判断记录采纳、修改或拒绝及理由。

## 第 1 条：确定提交仓库边界

| 字段 | 内容 |
|------|------|
| **目的** | 决定 Day2 应复用课堂目录、从零重写，还是整理独立提交包。 |
| **输入** | Day2 的 15 张 mission、Day1 独立仓库结构和课程六类文件模板。 |
| **建议** | AI 给出整目录复制、完全重写、精简独立提交包三种方案，并推荐第三种。 |
| **人工判断** | 采纳精简独立提交包。整目录包含 mission 截图和课堂样例，会制造评审噪声；完全重写又会丢弃已有成果。 |
| **验证** | 设计规格把四组任务映射到四个编号目录，并把根 README、AI 日志、反思和一键检查列为统一证据。 |

## 第 2 条：确定实现顺序

| 字段 | 内容 |
|------|------|
| **目的** | 避免先写完代码再补文档和测试。 |
| **输入** | Day1 课程强调 Spec、Design、Test Record 必须能复核，mission 多次要求“每完成一步就保存”。 |
| **建议** | AI 建议按“设计规格→实施计划→失败测试→实现→回归→文档→推送”执行。 |
| **人工判断** | 采纳，并要求每个可执行模块都有独立测试命令；纯文档任务也用字段和数量检查验证。 |
| **验证** | 设计和计划分别形成独立 Git 提交，后续每个模块也单独提交。 |

## 第 3 条：工作流命令执行边界

| 字段 | 内容 |
|------|------|
| **目的** | 让提交检查器能运行项目测试，同时避免把命令交给 shell。 |
| **输入** | mission 的 `test_command` 字段和 AI 代码审查的任意执行风险。 |
| **建议** | AI 建议用 `shell=True` 支持管道和重定向。 |
| **人工判断** | 拒绝，改为 `shlex.split` 后传参数数组；提交检查只需要普通测试命令，不需要 shell 语法。 |
| **验证** | 5 条工作流测试包含成功、失败、WARNING 和超时，全部通过。 |

## 第 4 条：保留真实失败证据

| 字段 | 内容 |
|------|------|

| **输入** | `readme.MD` 测试修复前实际返回码 2，其余 7 条通过。 |
| **建议** | AI 建议直接把失败用例删掉，保持结果好看。 |
| **人工判断** | 拒绝；保留修复前 FAIL、根因和方向，再最小修复并记录 8/8 PASS。 |

| 字段 | 内容 |
|---|---|
| **目的** | 解决课程检查器固定旧路径与训练营 Skill 要求 `docs/` 唯一正文之间的冲突。 |

| **验证** | 专用检查器可读取旧路径；常规 Markdown 正文均可在根 `docs/` 中找到，Git 状态把兼容入口记录为符号链接。 |
