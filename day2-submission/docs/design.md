# Day 2 仓库级设计与取舍

## 1. 总体方案比较

### 方案 A：四个独立最小工程 + 根级证据索引

- 优点：每个 Mission 有清楚边界、独立测试和局部 AI 日志；根 README 可一键复现。
- 成本：需要维护编号目录与仓库级验收映射。
- 风险：课程旧路径与统一 `docs/` 容易冲突。
- 两天可交付性：高，现有 30 条测试可分组定位失败。

### 方案 B：合并为单个大型 Agent 应用

- 优点：表面上入口更统一，可共享工具。
- 成本：Spec Coding、学习 Demo、工作流和安全审查边界混杂。
- 风险：难以判断每张 Mission 的独立完成度，失败定位与证据归属变差。
- 两天可交付性：低。

### 人工选择

选择方案 A。课程按独立 Mission 验收，编号工程能保持需求、实现、测试和局部日志的一一对应；根级文档只负责统一约束、复现和证据索引。

## 2. 总体数据流

```text
课程任务与硬性清单
  → 仓库级 Spec / Design / Tasks
  → 01 工作流：文件 + 测试 → 三状态报告
  → 02 Spec Coding：规则 → CLI → Eval → 测试记录
  → 03 学习 Demo：最小问题 → LangChain 链 → 离线验证 / 同桌评审
  → 04 Agent：用户请求 → 工具 → Validator → 回答 / 拒答
  → 根 check-submission.sh + Skill 审计
  → Git 提交
```

## 3. 模块与接口边界

| 模块 | 负责 | 不负责 | 主要证据 |
|---|---|---|---|
| 01 提交工作流 | 检查必需文件、运行结构化命令、判三状态 | 修改被检查项目 | `docs/01-submission-workflow/` |
| 02 任务助手 | 固定 Day 2 文件进度、三条 CLI、Eval | 检查真实文件内容、多人协作 | `docs/02-task-assistant/` |
| 03 学习 Demo | 验证 PromptTemplate 与 RunnableSequence | 真实模型效果、完整 RAG | `docs/03-learning-demo/` |
| 04 训练营 Agent | FAQ、任务工具、提交校验与 Validator | 任意文件读取、通用聊天 | `docs/04-training-agent/` |

## 4. 文档目录取舍

课程检查器硬编码根 `ai-log.md`、`reflection.md` 和各任务旧路径；项目 Skill 要求过程正文只在 `docs/`。复制两份会造成内容漂移，修改检查器又会偏离老师验收。因此使用 Git 符号链接作为兼容入口：正文只有一份，旧路径仍可被 `-f`、`grep` 和评审打开。

## 5. 失败与风险处理

- 工作流执行命令使用参数数组而非 `shell=True`，避免把可配置命令扩大为任意 shell。
- 任务助手状态损坏时重建默认结构并提示用户，不静默吞错。
- Demo 固定本地 fake model，依赖安装失败与模型逻辑失败分开处理。
- Agent 使用 `Path.resolve()` 和允许根包含判断，覆盖绝对路径、`..` 与符号链接逃逸。
- `unsafe_agent.py` 是明确的审查输入，禁止运行或导入。

## 6. 残留风险

- 符号链接在某些非 Git 拷贝工具或 Windows 解压方式中可能被展开或丢失；Git clone 和 GitLab 浏览支持该结构。
- LangChain 只验证同步 `.invoke()`，未验证批处理和异步异常传播。
- 同桌评审的真实 API 端到端未验证，结论保持 WARNING。
- 安全审查范围是指定夹具，不代表全仓库深度安全扫描。
