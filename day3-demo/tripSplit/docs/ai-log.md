# AI 协作日志 — TripSplit

> 记录每次与 AI 协作的决策链，每条包含：目的 / 输入 / 建议 / 人工判断 / 验证。
> **关键决策标记**：🔴 拒绝 AI 建议 / 🟡 修改 AI 建议 / 🟢 采纳但有附加条件

---

## 阶段一：需求定义

### 记录 1：数据存储方案 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定 TripSplit 的数据存储方式 |
| **输入** | 初始需求描述、项目定位（本地 Web 工具） |
| **建议** | AI 建议两种方案：(1) 前端 localStorage / IndexedDB，纯前端应用无需后端；(2) 后端服务器 JSON 文件，前端通过 API 读写 |
| **人工判断** | **拒绝方案 1**。采纳方案 2。理由：后端用 Python 方便测试功能验证，前后端分离便于后续扩展，也符合课程要求的技术栈 |
| **验证** | PRD 技术约束：前端 React + Vite、后端 FastAPI、测试 pytest、存储 JSON 文件 |

### 记录 2：前端框架选型 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定前端框架 |
| **输入** | 项目定位（本地工具）、需求规模（功能有限） |
| **建议** | AI 列出三种方案：(1) 纯 React + Vite 最轻量；(2) Next.js 功能全；(3) Vue 可替代 |
| **人工判断** | **拒绝 Next.js 和 Vue**。采纳 React + Vite。理由：本地工具用不上 SSR，Next.js 过重；明确要求"最轻量的前端框架" |
| **验证** | PRD 技术约束中锁定 React + Vite |

### 记录 3：成员管理策略 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 确定成员的增删改规则 |
| **输入** | 典型使用场景（3 人南京游）、账单与成员的关联关系 |
| **建议** | AI 建议支持成员编辑和删除，提示"已有账单时删除会很复杂"，建议加确认弹窗或级联删除 |
| **人工判断** | **拒绝编辑和删除**。采纳"只增不改不删"。理由：成员是虚拟角色不是账号，简单名字能区分就行；不删除避免了账单关联的复杂性 |
| **验证** | PRD 中成员定义：名字必填、不重复、不可编辑、不可删除 |

### 记录 4：结算触发方式 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定结算是实时计算还是手动触发 |
| **输入** | 账单可编辑删除的业务规则、用户体验考虑 |
| **建议** | AI 建议实时结算——每次编辑删除账单后自动重算 |
| **人工判断** | **拒绝实时结算**。采纳手动点击触发。理由：账单录入阶段频繁编辑修改，实时结算没有意义；只需最终需要结果时点击产出即可 |
| **验证** | PRD P0-5：点击"生成结算" → 展示结果 |

### 记录 5：结算算法精度 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 确定最小化转账次数的算法策略 |
| **输入** | 结算需求：转账次数尽量少、总金额对得上 |
| **建议** | AI 提示精确最优解是 NP-hard，建议启发式算法；列出贪心和精确方案对比 |
| **人工判断** | **拒绝精确方案**。采纳贪心算法。理由：旅行 AA 场景人数 2-8 人，贪心完全够用，不需要过度设计 |
| **验证** | PRD 结算规则：贪心匹配，每次取最大应收人和最大应付人 |

### 记录 6：移动端适配 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定是否做移动端响应式适配 |
| **输入** | 旅行场景下用户可能用手机记账的实际需求 |
| **建议** | AI 建议做响应式设计，提示旅行场景用户大概率用手机 |
| **人工判断** | **拒绝移动端适配**。理由：项目定位是本地 Web 工具，桌面优先；不做适配降低复杂度，聚焦核心功能 |
| **验证** | PRD 非目标明确列出"不做移动端适配" |

### 记录 7：数据导出功能 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 确定是否支持账单明细导出 |
| **输入** | 已有"复制结算摘要"功能、用户体验考虑 |
| **建议** | AI 建议增加 CSV/Excel 导出功能 |
| **人工判断** | **拒绝导出**。理由：核心需求是算清楚谁转给谁多少钱，结算摘要文本够用；导出不在 MVP 范围内 |
| **验证** | PRD 非目标列出"不做数据导出" |

### 记录 8：需求优先级分层 🟢

| 字段 | 内容 |
|------|------|
| **目的** | 将功能需求按 P0/P1/P2 分层 |
| **输入** | 前 7 条决策结论、任务文件的 PRD 规范（P0 少而硬、P1 增强、P2 可选） |
| **建议** | AI 按金字塔结构分层：P0 核心闭环 6 条、P1 基础增强 6 条、P2 体验优化 3 条 |
| **人工判断** | 采纳分层结构，**但有附加条件**：P0 必须包含"复制结算摘要"——没有这个功能核心闭环不完整 |
| **验证** | PRD 中 P0 共 6 条需求均有可测验收条件 |

### 记录 9：支出分类设计 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 确定账单分类的预设值和扩展性 |
| **输入** | 旅行消费常见场景、用户回答"预设几个常见的分类，然后加一个自定义兜底" |
| **建议** | AI 建议预设 10+ 分类（住宿、餐饮、交通、门票、购物、娱乐、医疗、通讯等） |
| **人工判断** | **砍掉大部分预设**。保留 5 个：住宿、餐饮、交通、门票、购物；兜底"其他"可自定义。理由：分类过多增加选择负担，5 个覆盖主要场景 |
| **验证** | PRD P1-6：预设 5 个 + 其他自定义 |

## 阶段二：PRD 补充决策

### 记录 10：均摊精度与尾差 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定均摊尾差的处理规则（如 100 元 3 人均摊） |
| **输入** | PRD 中"参与人均摊"的定义未覆盖尾差场景 |
| **建议** | AI 列出三种方案：(1) 尾差归付款人；(2) 尾差归第一人；(3) 结算时补偿精度误差 |
| **人工判断** | **拒绝专门处理尾差**。直接除法，不做任何尾差补偿。理由：系统对金额精确性无高要求 |
| **验证** | 结算算法不涉及尾差逻辑，简单均分即可 |

### 记录 11：账单日期约束 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定账单日期是否必须在旅行日期范围内 |
| **输入** | PRD 说账单日期默认当天可修改，但未定义边界 |
| **建议** | AI 建议限制在旅行日期内 |
| **人工判断** | **拒绝日期约束**。理由：时间只是记录，用户可能提前预订或事后补录 |
| **验证** | 账单日期字段无范围校验 |

### 记录 12：数据存储结构 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 确定后端 JSON 文件的存储方式和组织结构 |
| **输入** | PRD 只说"后端本地 JSON 文件"，未定义路径、文件组织、ID 策略 |
| **建议** | AI 建议讨论多种方案：每个旅行一个文件 / 单一大文件、UUID / 自增 ID 等 |
| **人工判断** | **简化为单一大文件**。一个 JSON 文件存所有旅行数据。理由：没有多用户，数据量小，MVP 能演示就行 |
| **验证** | 确认存储路径 `backend/data/trips.json` 写入 plan.md |

## 阶段三：实现计划

### 记录 13：页面布局方案 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 确定旅行详情页的布局结构 |
| **输入** | PRD 需求：成员管理、账单列表、结算展示需在同一页面 |
| **建议** | AI 提供三种方案：(A) 上下分区；(B) 左右分栏；(C) 左侧固定+右侧滚动 |
| **人工判断** | **拒绝方案 A 和 C**。采纳方案 B 左右分栏。理由：成员和账单并列展示空间利用率高，一屏看完 |
| **验证** | ASCII 布局图写入 plan.md |

### 记录 14：结算精度处理 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定结算算法中浮点数比较的精度策略 |
| **输入** | 均摊除法可能产生浮点残留（如 10/3 = 3.33333...） |
| **建议** | AI 建议用 ±0.005 浮点阈值做比较 |
| **人工判断** | **拒绝浮点阈值**。改为 round 保留两位小数 + == 0 比较。理由：简单 round 够用，阈值比较增加不必要的复杂度 |
| **验证** | settle.py 算法中所有金额运算后 round(v, 2)，比较用 == 0 |

### 记录 15：账单变更后结算处理 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 确定编辑/删除账单后，旧结算结果如何处理 |
| **输入** | PRD 说账单可编辑删除，结算可重新生成，但未定义联动规则 |
| **建议** | AI 讨论两种方案：(A) 自动清除旧结算；(B) 保留旧结算，用户手动重新生成 |
| **人工判断** | **采纳方案 A**。账单变了旧结算作废，自动清除。理由：避免用户看到过期结算结果 |
| **验证** | PUT/DELETE expense 端点同时清除 settlement 字段 |

### 记录 16：删除复制摘要功能 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定结算结果是否支持复制/导出 |

| **建议** | AI 建议保留复制功能，方便用户发到微信群 |
| **人工判断** | **拒绝复制和导出**。结算纯前端展示。理由：不需要复制功能，生成结算就是前端展示即可 |
| **验证** | PRD P0-6 改为"结算结果展示"，plan 删除复制按钮 |

### 记录 17：编辑账单字段保留策略 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 确定编辑账单时未传字段的处理方式 |

| **建议** | AI 讨论两种方案：(A) 未传字段清空；(B) 未传字段保留原值 |
| **人工判断** | **采纳方案 B**。未传字段保留原值。理由：编辑场景通常只改部分字段，保留原值更符合用户预期 |
| **验证** | PUT expense 端点合并更新，只覆盖传入字段 |

### 记录 18：成员统计实现方式 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定成员统计概览（已付/应付/余额）的数据来源 |
| **输入** | PRD P2-2 要求详情页展示成员统计 |
| **建议** | AI 讨论两种方案：(A) 后端单独提供统计接口；(B) 前端从 expenses 实时计算 |
