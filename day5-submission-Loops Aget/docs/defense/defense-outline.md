# 六分钟答辩大纲

## 00:00–00:50 问题诊断

项目已有规则、文本和图像机器学习流水线，但 LLM 侧最初只有简单调用。真实审核系统不只要判断类别，还要调用工具、处理冲突、恢复状态、限制模型权限并提供证据。因此目标不是“换一个更长提示词”，而是把 ML 基线升级为 Agent 与 ML 并存的内容审核系统。

## 00:50–01:40 三方案与取舍

- 方案 A：ML 流水线，速度快、成本低，复杂图文解释弱。
- 方案 B：单多模态模型，接入快，但缺少工具、路由、权限和恢复。
- 方案 C：ML 快速方案 + 条件式 LangGraph Agent，工程复杂度最高，但最符合可审计与可恢复目标。

最终选择 C。当前实现了两条能力与对比看板，下一步再把统一在线风险路由接通。

## 01:40–03:10 Agent 判断链

```text
规则预检
  ├─ 可信硬规则 → 确定性策略门
  └─ 继续分析 → DeepSeek 文本取证 + 豆包视觉取证
                        ↓
                    风险路由
              ├─ 一致低风险 → 策略门
              └─ 冲突/高风险 → Critic → Arbiter → 策略门
                                                    ↓
                                    放行 / 拦截 / 人工复核
```

关键判断：

1. LLM 只产 Evidence，不拥有硬规则权限；
2. 图片必须由豆包多模态取证；
3. 简单内容不必进入完整辩论；
4. 必要证据缺失时不静默放行；
5. 人工决定恢复同一 `run_id/thread_id`。

## 追问卡

### 为什么不用一个大模型直接判？

因为用户内容不可信，单模型同时取证和裁决会把提示注入、格式错误和模型故障集中到一个黑盒。当前设计把 Evidence 与 Policy Authority 分离，关键权限可以单元测试。

### 为什么还保留机器学习？

Agent 在复杂图文和审计上更强，但调用慢、成本高。旧 ML 对稳定低风险流量更适合，所以最合理的是按风险分流，而不是用新技术替换所有旧资产。

### 模型挂了会不会放过违规内容？

不会默认放行。Agent 异常会生成不可用 Evidence；必要来源缺失、仲裁不确定或模型失败时策略门转人工，Graph 无 decision 时 run 标记 failed。

### 如何防止 LLM 伪造硬规则？

策略门不仅看 `HARD_BLOCK_*` 名称，还检查 Evidence 来源。只有本地 `rule` 或 `attack_tool` 能产生有效硬拦截。

### 图片真的审了吗？

视觉 Agent 会把本地 JPEG/PNG/WebP 校验后转换为 data URL，通过方舟 Responses API 发送给 `doubao-seed-2-0-lite-260428`。本轮安全图片烟测返回 allow 和 1 条 Evidence；这只证明接口与协议可用，不代表真实审核准确率。

### 为什么看板数字这么大？

这些是固定随机种子生成的演示快照，用于同一口径比较架构。页面显示数据源，文档也不把它们解释为生产流量或模型实测。
