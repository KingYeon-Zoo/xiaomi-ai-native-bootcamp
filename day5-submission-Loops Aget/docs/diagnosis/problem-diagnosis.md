# 问题诊断

## 现状

项目最初以机器学习审核流水线为基线：规则引擎、文本分类、图像分类、图文相关性和融合决策已经形成较完整能力。Git 基线 `973ab58` 可以证明这些资产存在。后续 `llm_api` 路线若只用一次提示词返回结果，虽然开发快，却不能回答真实系统必须面对的问题：模型调用了什么工具、为什么升级、如何处理冲突、失败后如何恢复、谁有最终权限。

## 目标

在不推翻旧 ML 资产的前提下，增加一条完整 Agent 深度审核路线，并让前端用同一演示口径呈现两种方案：

1. 低风险、稳定分布、高吞吐内容可由 ML 快速处理；
2. 图文冲突、高风险、低置信和提示注入进入 Agent 深度审核；
3. LLM 负责结构化取证，不拥有硬规则权限；
4. 模型不可用或证据不足时不静默放行；
5. 人工决定能从同一运行恢复；
6. 审查者能够从页面、接口、代码和测试四层复核判断链。

## 用户与利益相关方

| 角色 | 主要诉求 | 冲突或风险 |
|---|---|---|
| 发帖用户 | 尽快知道审核状态与简明原因 | Agent 深度审核会增加等待时间 |
| 人工审核员 | 获取证据、路由和待办 | 不应看到隐藏思维链或无关隐私 |
| 平台运营 | 控制漏放、误杀、成本和吞吐 | 单一路线难同时最优 |
| 项目维护者 | 复用 ML 基线并建立 Agent 能力 | 旧同步接口和模型指标不适配新状态 |
| 开源使用者与审查者 | 看见真实判断、取舍和验证 | 演示快照不能冒充生产指标 |

## 边界与失败定义

- 输入边界：当前支持文本、单张 JPEG/PNG/WebP；不覆盖视频、多图和超长批量任务。
- 权限边界：仅 `rule` 与 `attack_tool` 是硬政策可信来源；LLM 不能自授权限。
- 运行边界：单进程队列适合本地演示，不代表多实例可靠性。
- 数据边界：看板聚合值来自确定性演示快照，不代表线上真实流量。
- 失败定义：必要证据缺失、模型异常或仲裁不确定时进入人工；Graph 无 decision 时 run 标记 failed。

## 非目标

当前版本不重训旧模型，不声明生产准确率，不建设多实例任务平台，不补写无法核验的历史过程，也不把演示快照解释为线上真实数据。

## 成功标准

1. 文本和图片分别由对应 Agent 生成可校验 Evidence。
2. 硬规则短路、快速路径、仲裁路径和人工路径均有测试。
3. 同一 `run_id` 可查询状态、查看结构化轨迹并完成人工恢复。
4. Agent/ML 看板可切换并明确数据来源。
5. 后端 Agent 测试、前端 lint/build、启动健康检查和文档一致性审计有实际记录。
6. 文档明确区分实现事实、演示数据、设计假设和证据缺口。

## 当前信息缺口

- 仓库没有官方题号、正式标注集、生产 SLO 或内容政策版本。
- Git 只显示一个提交署名，因此本仓库按个人维护项目记录责任边界。
- 没有产品环境的政策签字、SLO 与标注集评测记录。
- 文档重构前的云烟测没有独立日志文件，因此旧声明未直接沿用；当前版本已重新执行最小文本与图片烟测。
