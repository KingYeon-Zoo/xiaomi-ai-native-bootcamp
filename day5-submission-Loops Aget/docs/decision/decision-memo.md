# 决策备忘录

## 最终决策

选择“方案 C：条件式 Agent 与 ML 双方案”。

- Agent 主链使用 LangGraph `StateGraph`。
- DeepSeek 负责文本、critic、arbiter；豆包负责视觉。
- 旧规则引擎作为可信工具，`ModerationPolicy` 作为最终自动裁决门。
- 风险路由决定快速路径或 critic/arbiter 路径。
- 缺证据、不确定或模型不可用进入人工复核。
- Mongo 保存 run 与 checkpoint，人工决定恢复同一 `run_id/thread_id`。
- 前端默认展示 Agent，同时保留 ML 与同口径对比视图。

## 为什么这样选

它没有丢弃原始 ML 基线，而是把传统模型的速度优势与 Agent 的深度证据能力组合起来，并把设计落实到可运行的工具、状态、路由、HITL 和失败测试中。与单提示词相比，权限更清楚；与全量辩论相比，保留了控制成本的路径。

## 接受的代价

- 需要维护两套指标语义和更多状态；
- 多模型协议需要结构化校验与失败处理；
- 单进程 runtime 只能作为演示 MVP；
- 双方案看板的 KPI 是演示快照，不是生产测量；
- 统一 ML→Agent 在线路由仍需后续实现。

代码证据为 C01–C09，测试证据为 T01–T07，见 `docs/evidence-map.md`。用户在需求同步中明确选择方案 C、接受分层裁决，并指定豆包审查图片。
