# Day3 个人复盘

## 我做了什么

本次没有重写老师已经确认正确的 TripSplit 代码，而是把 demo 作为基线，按 Day3 八项题纲重新检查产物流转，并依据训练营 skill 增加工程约束、实际测试记录、来源说明和提交审计。这一选择减少了无价值改动，也避免把老师实现包装成个人原创。

## 一个主动取舍

我拒绝为了“看起来更像自己的项目”而改技术栈或增加新功能。Day3 的重点是 PRD、方案、开发、测试、质量关卡、Skill/MCP/Harness 和 Token 策略如何串起来，而不是扩充功能。保留 Web + FastAPI + JSON 的既定方案，能把精力用于验证证据链。

## 一个失败带来的修正

第一次启动后端冒烟测试时，工作目录已经在 `backend/`，命令却仍带 `backend/` 前缀，导致服务没有启动。修正路径后请求 `/trips` 成功。这说明 README 和测试记录应给出“从哪个目录执行”的完整上下文，不能只写一个看似正确的命令。

## 风险与下一步

- 本次没有执行浏览器手动 E2E，不能把 demo 中的历史 E2E 结论当作个人验证结果。
- JSON 存储不支持可靠并发写入，但符合单机课程 demo 的范围。
- 如果继续迭代，优先把 10 步 E2E 自动化，而不是先加入登录或云数据库。
