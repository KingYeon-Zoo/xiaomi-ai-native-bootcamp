# Day4 个人反思：从“代码能跑”到“结论值得被接受”

## 1. 最难的不是模型，而是守住口径

这次最具体的教训来自“模块 Error 率”。初看它很像一个普通百分比，我很自然地把某模块 Error 数除以全部 Error 数。这个公式能运行、能画图、数值也落在 0 到 1 之间，因此很容易逃过只检查类型和非空的测试。但题目定义的分母是“该模块全部日志数”。前者回答“错误集中在哪里”，后者回答“模块自身有多不稳定”，是两个不同问题。若拿前者给运维排查排序，流量最大的模块会天然显得更危险。

这让我重新理解了 Agent 生成代码的主要风险：它经常不是语法错误，而是生成一个形式正确、语义近似、看起来合理的替代指标。以后面对任何比例，我会先写清分子、分母和业务问题，再写实现；测试必须专门构造“两个公式结果不同”的反例，而不是只断言结果存在。

## 2. 我拒绝了“把所有材料做得更完整”的诱惑

Demo 有大量 PRD、Design、Dev、Handoff 和旧检查脚本。复制它们会让提交显得很厚，但最新数据说明明确要求把需求、设计、任务和变更合并到 `spec.md`，且不再单独提交这些文档。我选择删除文档数量，增加每份文档内部的证据密度。这不是偷懒：多份重复正文会产生版本漂移，评审者反而不知道哪个口径有效。

同样，我没有加入 Linux.log、多语言模型、OCR、Web UI 或深度学习。课程数据足以验证日志解析和经典文本分类，继续扩展会把时间从边界测试、泄漏检查和误判分析上拿走。Day4 的“主动收窄”不是做得少，而是只保留能给出真实证据的部分。

## 3. raw/cleaned 双轨让我看到“清洗越多越好”是错的

如果先把邮件转小写、删除标点和货币符号，再计算大写比例、感叹号和货币特征，这些特征会稳定变成 0。流水线仍然可以训练，甚至可能达到不错的 Accuracy，但实现已经违背数据契约。为避免仅靠文档提醒，我把特征函数设计成同时接收 `raw_message` 与 `cleaned_message`：接口本身迫使调用者面对两个来源。

这也改变了我对“清洗”的理解。清洗不是把信息统一删掉，而是为不同消费者准备不同视图。词袋模型需要规范化文本，人工规则需要保留语气和符号；一份数据不能同时假装满足两种目的。

## 4. 一次不应掩饰的流程偏差

本次我先读了题目、评分表和 Skill，再快速落了实现骨架，完整的 `engineering-constraints.md` 是之后才写入仓库。这不符合“工程约束文件先落盘”的门禁。即使脑中已有约束，未写入文件就无法约束后续 Agent，也无法让第三方复核当时的判断。

我没有在 AI-log 中把顺序改写成理想化的 TDD 故事。补救措施是立即建立事实基线、验收映射和待验证状态，并在任何 PASS 产生前完成约束与测试记录。下次的改进不是“提醒自己更认真”，而是在项目初始化脚本中把 `docs/engineering-constraints.md`、任务清单和测试记录设为业务代码目录创建前的硬检查；缺少时让审计脚本直接 BLOCKED。

## 5. 关于指标的克制

朴素贝叶斯达到门槛也不等于可部署。SpamAssassin 数据来自 2003—2005 年，随机切分主要检验同分布复现；它不能证明对当代钓鱼邮件、多语言内容、图片附件或时间漂移有效。规则模型若召回较低，也不应通过反复查看最终测试集调阈值“修到好看”。真正的下一步是增加验证集并按 `hard_ham`、数据批次和时间做分层评估。

我认为这次最重要的转变是：验收对象不再只是代码，而是一条结论。只有当数据来源、变换口径、训练边界、失败样本和修改范围都能被复核时，我才有理由说“这次修改更值得接受”。
