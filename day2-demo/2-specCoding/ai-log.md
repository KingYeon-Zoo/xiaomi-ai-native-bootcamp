# AI 协作日志 — Day2 学习任务清单助手

> **核心原则**：AI 提供建议，人类做决策。每条记录的「人工判断」字段是关键——必须写清你采纳/修改/拒绝了 AI 的什么建议以及为什么。

**五字段规范**：目的 / 输入 / 建议 / 人工判断 / 验证
**关键决策标记**：
- 🔴 拒绝 AI 建议
- 🟡 修改 AI 建议
- 🟢 采纳（可能有附加条件）

**统计**：共 16 条记录，其中 🔴 拒绝 5 次 / 🟡 修改 7 次 / 🟢 采纳 4 次

## 阶段一：Spec 定义

### 记录 1：命令形式 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定项目整体结构和命令形式 |
| **输入** | `任务.txt`（5 步流程 + 交付文件要求） |
| **建议** | AI 提出三种方案：A. 单文件多子命令（`cli.py today`）；B. 三个独立脚本；C. 使用 click 库实现更专业的 CLI |
| **人工判断** | **拒绝方案 B 和 C**。采纳方案 A。理由：方案 B 三个独立脚本过于分散，用户体验割裂；方案 C 引入第三方依赖（click），项目太小不值得，argparse 标准库足够 |
| **验证** | 确认 `python cli.py today / submit / check` 三种调用方式 ✅ |

### 记录 2：存储方式 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定任务列表和提交状态的存储方式 |
| **输入** | 项目规模（小型命令行工具） |
| **建议** | AI 提出三种方案：A. SQLite 数据库；B. JSON 文件；C. 纯文本文件 |
| **人工判断** | **拒绝方案 A 和 C**。采纳方案 B。理由：SQLite 引入数据库依赖，项目只有 5 个文件，杀鸡用牛刀；纯文本文件解析复杂，容易出错；JSON 简单直观，易于读写调试 |
| **验证** | 确认 `status.json` 结构：`{"spec.md": false, "plan.md": false, ...}` ✅ |

### 记录 3：Spec 完整性 Review 🟢

| 字段 | 内容 |
|------|------|
| **目的** | 检查 spec.md 是否覆盖任务要求 |
| **输入** | `spec.md`、`任务.txt`（最低要求：非目标 ≥2、边界 ≥2、验收 ≥2） |
| **建议** | AI 生成 spec 初稿，包含目标 3 条、非目标 3 条、边界 5 条、验收 6 条 |
| **人工判断** | **采纳全部**。理由：覆盖正常和异常路径，符合最低要求 |
| **验证** | 逐条检查：目标 ✅、非目标 ✅、边界 ✅、验收 ✅ |

## 阶段二：Design 设计

### 记录 4：模块划分 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 确定项目模块结构 |
| **输入** | 项目规模（小型命令行工具）、spec.md 的 3 个命令 |
| **建议** | AI 提出两种方案：A. 单文件 3 个职责；B. 多文件拆分（cli.py + tasks.py + storage.py） |
| **人工判断** | **拒绝方案 B**。采纳方案 A。理由：项目只有 3 个命令，拆成 3 个文件过度设计，增加维护成本；单文件内部分职责（函数划分）即可，代码量不超过 100 行 |
| **验证** | 确认 3 个职责：CLI 入口、任务管理、输出格式化 ✅ |

### 记录 5：数据结构 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 确定任务列表和提交状态的存储结构 |
| **输入** | spec.md（5 个固定文件名、status.json 存储） |
| **建议** | AI 提出 TASKS 字典硬编码 + status.json 存布尔值，建议用 0/1 表示状态 |
| **人工判断** | **修改状态表示方式**。采纳 TASKS 结构，但将 0/1 改为 true/false（布尔值）。理由：JSON 原生支持布尔类型，语义更清晰，代码中直接用 `if status[filename]` 判断，无需额外转换 |
| **验证** | 确认 TASKS 结构（5 项）和 status.json 格式（5 个布尔字段） ✅ |

### 记录 6：风险识别 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 识别项目潜在风险并制定应对策略 |
| **输入** | 数据结构设计、边界条件 |
| **建议** | AI 识别 5 个风险：文件删除、文件篡改、大小写不一致、并发写入、磁盘满 |
| **人工判断** | **拒绝并发写入和磁盘满**。采纳前 3 个。理由：这是单用户命令行工具，不存在并发场景；磁盘满是系统级问题，不是本工具应该处理的范围 |
| **验证** | 每个风险都有明确的应对策略 ✅ |

## 阶段五：实现与调试

### 记录 10：CLI 骨架 🔴

| 字段 | 内容 |
|------|------|
| **目的** | 创建 cli.py 骨架，实现命令行参数解析 |
| **输入** | `tasks.md`（Step 1）、`plan.md`（CLI 入口模块） |
| **建议** | AI 建议使用 click 库实现，认为更简洁、更专业 |
| **人工判断** | **拒绝 click**。采用 argparse。理由：click 是第三方依赖，需要额外安装；项目只有 3 个命令，argparse 标准库完全够用；减少依赖意味着更好的可移植性 |

### 记录 11：today 命令输出格式 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 实现 today 命令，输出任务列表 |
| **输入** | `plan.md`（TASKS 字典结构） |
| **建议** | AI 建议用表格形式输出（带序号、对齐），更美观 |
| **人工判断** | **修改为简洁列表**。理由：命令行工具追求简洁，表格在窄终端会错位；简单列表（`- filename: desc`）足够清晰，符合"学习任务清单"的定位 |
| **验证** | `python cli.py today` 输出 5 行任务信息 ✅ |

| 字段 | 内容 |
|------|------|

| **人工判断** | **采纳，但修复一个问题**：today 命令需要调用 load_status() 来触发初始化，AI 初稿遗漏 |

### 记录 13：check 命令输出格式 🟡

| 字段 | 内容 |
|------|------|
| **目的** | 实现 check 命令，列出未提交文件 |
| **输入** | `spec.md`（验收标准：全部完成提示） |
| **建议** | AI 建议用 emoji（✅/❌）标记每个文件的提交状态，一目了然 |
| **人工判断** | **修改为只列出未提交文件**。理由：spec.md 要求"返回尚未提交的文件清单"，不是返回全部状态；只列未提交更聚焦，符合"检查进度"的使用场景；全部完成时用"🎉 全部完成！"提示 |
| **验证** | 列出未提交文件 ✅、全部完成提示 ✅ |
