## 第 8 条：确定严格状态判定规则

| 字段 | 内容 |
|------|------|
| **目的** | 明确 `PASS`、`WARNING`、`BLOCKED` 的优先级和触发条件 |
| **输入** | 用户确认：必需文件缺失或任一测试失败/超时直接 `BLOCKED`；文件都在、测试都过才可能 `PASS`；当前版本不做深度质量扣分 |
| **建议** | AI 建议采用严格阻塞规则：必需文件缺失、测试失败、测试超时、无法运行测试都判为 `BLOCKED` |
| **人工判断** | 采纳严格规则。理由：该工作流定位是提交前检查助手，核心目标是防止不可评审或不可验证的提交包流出 |
| **验证** | 后续 `status-rules.md` 和 `check-submission.ps1` 必须体现 `BLOCKED` 优先级高于 `WARNING`，且测试失败不可降级 |

## 第 9 条：确定轻量 WARNING 条件

| 字段 | 内容 |
|------|------|
| **目的** | 在不做深度内容评审的前提下，为 `WARNING` 定义可执行的简单触发条件 |
| **输入** | 用户提出：可以用非常简单的方式检测 README 至少包含哪些项、ai-log 至少有 5 个标签，用来弥补 `WARNING` 条件 |
| **建议** | AI 建议 README 只检测是否出现安装、运行、测试三类线索；ai-log 只检测是否出现 5 个字段标签：目的、输入、建议、人工判断、验证 |
| **人工判断** | 采纳轻量检测。理由：这些检查不会评估内容好坏，但能发现明显缺漏；发现问题时只给 `WARNING`，不升级为 `BLOCKED` |
| **验证** | 后续 `checkFiles()` 需要输出 README 线索检查和 ai-log 标签检查结果，并写入最终报告 |
