# 个人项目执行规范

## 评分重点

突出个人如何理解题目、主动收窄范围、比较方案、修正 AI 建议并验证结果。功能完成只是证据链的一环。

## 建议最小产物

以题目提交清单为准；未规定时采用：

```text
项目根目录/
├── AGENTS.md
├── CLAUDE.md              # 仅在课程明确要求时
├── README.md
├── docs/
│   ├── engineering-constraints.md
│   ├── spec.md 或 prd.md
│   ├── design.md
│   ├── tasks.md
│   ├── ai-log.md
│   ├── test-record.md 或 test-strategy.md
│   └── reflection.md
├── src/
└── tests/
```

没有 `docs/` 时先创建。除根目录 `README.md`、`AGENTS.md` 和课程明确要求的 `CLAUDE.md` 外，所有开发过程文件必须使用 Markdown 并放入 `docs/`。不要为了匹配目录而重复已有文档；建立清楚的等价映射即可。

## 工程约束文件必须写清

完整正文写入 `docs/engineering-constraints.md`；根目录 `AGENTS.md`/`CLAUDE.md` 只写读取该正文的入口规则。正文必须写清：

1. 题目、角色、时间限制和最终提交要求。
2. 资料优先级，以及哪些数据或原始要求只读。
3. 可验证目标、主动不做的事项和边界条件。
4. “先文档、后实现、边做边留证据”的阶段门禁。
5. 允许修改范围和禁止无关重构、无依据扩展、伪造结果。
6. 真实安装、运行、测试和提交审计命令。
7. 验收标准到实现、测试、证据的映射。
8. 当前已验证事实、待验证技术点和残留风险。
9. AI 协作五字段及人工判断要求。
10. PASS/WARNING/BLOCKED 完成定义。

## 开发节奏

1. 保存原题和评分表，不改写原始事实。
2. 写工程约束文件和 Spec/PRD。
3. 在 `docs/` 中提出至少两种实质方案，记录选择与拒绝理由。
4. 写 `docs/design.md` 和 `docs/tasks.md`。
5. 按任务最小实现，每完成一项就运行对应测试。
6. 同步 `docs/` 中的测试实际结果和关键 AI 决策。
7. 从干净入口执行 README 命令。
8. 运行项目专用检查器和本 Skill 审计脚本。
9. 用证据路径准备个人答辩，不背诵功能列表。

## Bug 修复模式

严格采用：复现 → 定位 → 至少两个根因假设 → 最小修复 → 正常/边界/异常回归。所有复现、根因、修复和回归记录使用 Markdown 写入 `docs/bugs/` 或题目指定的 `docs/` 子目录；保留修复前失败和修复后通过的证据。

## 高分自查

- 能否指出一个被主动砍掉的功能及理由？
- 能否指出一个 AI 建议被修改或拒绝的真实例子？
- 每条验收标准是否有实际结果，而不是计划？
- 失败或边界用例是否推动过修正或风险更新？
- README 是否能让同学不询问作者就复现？
- 工程约束文件是否能阻止 Codex 过度设计和越过阶段门禁？
