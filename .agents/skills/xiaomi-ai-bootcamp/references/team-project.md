# 团队项目执行规范

## 评分重点

除可复核交付外，必须证明团队如何诊断问题、处理分歧、分配责任、审查 AI 建议、验证端到端链路，以及每个人做出了什么可定位的贡献。

## 使用官方团队模板

优先参考 `day5/day5材料/project-template-master/`，但把其中所有过程 Markdown 统一收口到当前项目的 `docs/`。不要只创建页面和代码；同步维护诊断、方案、决策、协作、AI、设计、验证、复盘、原型说明和答辩证据。

模板原本位于 `prototype/` 的 Markdown 说明迁移为 `docs/prototype/prototype-readme.md` 和 `docs/prototype/screenshots-or-video.md`；`prototype/` 只保留可执行原型、静态资源或代码，不重复保存过程文档。

## 强制链路

```text
问题诊断
→ 澄清问题
→ 假设与非目标
→ 三个本质不同的方案
→ 取舍矩阵与拒绝方案
→ MVP 决策
→ 端到端系统设计
→ 原型实现
→ 正常/边界/失败/回归/端到端验证
→ Review 与风险更新
→ 最终建议、团队复盘和答辩
```

## 模板中的最低要求

- 澄清问题不少于 10 个，其中至少 3 个 P0；P0 必须说明不同答案如何改变方案。
- 至少 3 个本质不同的方案，不能只是同一方案的低/中/高配。
- 至少 2 个被明确拒绝或明显修改的 AI 建议。
- AI 协作覆盖六类中的至少五类：澄清、对比、反证、实现、验证、Review；反证或风险审查必须存在。
- 至少 4 次会议或同步纪要：启动、方案取舍、中期同步、提交前复盘。
- 验证至少覆盖 2 个正常、2 个边界、2 个失败、1 个回归和 1 个端到端场景。
- 至少 3 个边界或失败样例由团队自行设计。
- 至少 1 次 AI Review 后产生人工修正。
- 每名成员至少留下 3 类贡献证据，并写 150–300 字个人说明。

若最新题目或评分表更改数量，以最新要求为准，并在决策记录中说明变化。

## 团队工程约束文件额外内容

1. 成员、角色、主负责人、备份人和模块边界。
2. 每个任务的交付物、截止时间、验收标准和证据位置。
3. 分支、提交、合并和 Review 规则。
4. 会议、Issue、决策和 AI 协作日志的更新时机。
5. 端到端责任映射，避免“前端完成、后端完成、链路未完成”。
6. 冲突升级方式，以及谁有最终范围决策权。
7. 代码、文档、测试相互 Review 的提交门禁。
8. Demo 失败时的截图、录屏或静态证据兜底。

完整工程约束正文固定为 `docs/engineering-constraints.md`。根目录 `AGENTS.md`/`CLAUDE.md` 只负责让工具读取该正文；会议、任务、Issue、决策、Review 和个人贡献记录全部写入 `docs/` 对应子目录。

## 会议与决策纪律

- 会议必须产生结论、行动项、负责人、验收和证据位置。
- 分歧不是扣分项；不记录分歧及解决过程才是风险。
- 关键决策回答：有哪些选项、为何现在决定、证据是什么、代价是什么、谁验证。
- 不得虚构会议、成员确认或人工意见；缺席或未确认要按真实状态记录。

## 答辩准备

围绕判断链路组织 6 分钟展示：真正问题 → 方案取舍 → 端到端设计 → MVP 主路径与失败场景 → 验证和风险 → 个人贡献。每个说法都指向 `docs/` 中的具体 Markdown 证据，不临场新增无证据结论。
