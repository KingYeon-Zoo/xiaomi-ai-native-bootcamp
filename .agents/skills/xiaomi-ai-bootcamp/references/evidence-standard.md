# 可复核交付标准

## 评价原则

第三方无需询问作者，只依靠提交文件和可执行命令即可判断项目是否满足要求。功能复杂度不能替代证据完整度。

## 文档位置硬约束

- 每个项目必须存在 `docs/`；没有就先创建。
- 所有开发过程文件使用 Markdown，并以 `docs/` 或其子目录为唯一正文位置。
- 根目录只保留项目总览 `README.md`、Codex 发现入口 `AGENTS.md`，以及课程明确要求时的 `CLAUDE.md`。
- 完整工程约束正文固定为 `docs/engineering-constraints.md`；根目录入口只负责路由。
- Spec/PRD、Design、Tasks、AI Log、测试记录、决策、会议、Issue、复盘、原型说明和答辩文档不得散落在根目录或 `prototype/`。
- 老师提供的课程材料、任务原文、模板、参考资料、输入数据和工具 Skill 是只读输入，不属于项目自产过程文档，保留原位。

## Day1 六类核心证据

| 文件 | 必须证明的内容 | 低质量信号 |
|---|---|---|
| `README.md` | 环境、安装、运行、测试、结构和限制 | 只有项目介绍；命令不可执行 |
| `docs/spec.md`/`docs/prd.md` | 目标、非目标、验收、边界 | 目标宽泛；没有非目标；无法测试 |
| `docs/design.md` | 数据流、模块、接口、技术取舍、失败处理 | 只写技术名词；没有为什么 |
| `docs/ai-log.md` | AI 参与、人工判断、验证结果 | 聊天截图；“AI 说得对”；没有验证 |
| `docs/test-record.md` | 输入、预期、实际、结果和环境 | 只写“全部通过”；缺少具体用例 |
| `docs/reflection.md` | 具体事件、困难、判断和下次改进 | “收获很多”“下次加油”等空话 |

任务材料使用其他文件名时，按“证明什么”映射，不机械复制 Day1 文件名。

## 证据链

每条关键需求至少形成以下映射：

```text
题目/评分项
→ Spec/PRD 验收标准
→ Design 模块或决策
→ Tasks 任务
→ 实现文件
→ 测试用例与实际结果
→ AI/人工决策记录
```

在工程约束文件中维护映射索引；详细内容留在对应文档，避免重复后失真。

## AI 协作记录五字段

| 字段 | 写法 |
|---|---|
| 目的 | 本次协作要解决的具体问题 |
| 输入 | 提供给 AI 的资料、约束、已有结论 |
| 建议 | AI 给出的主要方案或风险 |
| 人工判断 | 采纳、修改或拒绝了什么，以及理由 |
| 验证 | 用什么命令、用例、数据或 Review 证明判断可靠 |

“人工判断”是核心评分证据。不要为了显得独立而虚构拒绝；真实记录筛选和修改过程。

## 状态判定

| 状态 | 判定 |
|---|---|
| PASS | 必需文件存在且非空；无占位符；命令实际运行；验收与测试可追溯 |
| WARNING | 文件基本齐全，但内容、命令、映射、边界或人工判断不充分 |
| BLOCKED | `docs/` 缺失；过程 Markdown 位于 `docs/` 外；关键证据缺失；无法复现；测试失败；把未执行结果写成 PASS |

## 证据真实性红线

- 不伪造命令输出、测试数量、时间、提交记录、会议或人工反馈。
- 不把预期结果复制到“实际结果”。
- 不删除失败记录；记录失败如何改变设计或风险判断。
- 不把计划写成已完成，不把假设写成已验证事实。
- 不因检查脚本只检查文件存在，就忽略内容质量。
