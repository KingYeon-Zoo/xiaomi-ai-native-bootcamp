# 已有代码的逆向重构模式

## 原则

逆向重构的目标是让现有实现、当前判断和真实证据一致，不是伪造一条看似完整的历史过程。

## 证据等级

| 等级 | 来源 | 可写法 |
|---|---|---|
| A | 可运行测试、提交历史、代码、日志、截图元数据 | 可写为事实，并给路径或命令 |
| B | 多个文件互相印证、用户明确陈述 | 标明来源，不冒充运行验证 |
| C | 从实现推断的设计意图 | 写“根据当前实现推断”，等待确认 |
| D | 无证据的合理猜测 | 不写成项目事实，只列为待确认 |

## 执行顺序

### 1. 冻结基线

- 记录当前分支、工作区状态和已有用户改动。
- 不重写 Git 历史，不覆盖现有文档，不删除失败证据。
- 运行最小启动、单元、集成或端到端命令，保留真实输出。

### 2. 建立实现清单

从入口、路由、服务、数据模型、配置、测试和 UI 页面恢复：

- 实际支持的用户和角色；
- 技术端和调用关系；
- 输入、状态、规则、AI 调用与输出；
- 人工复核点和日志；
- 失败处理；
- 已实现但无题面价值的功能；
- 文档声称但代码没有的功能。

### 3. 反向映射评分链

为每个现有核心功能建立：

```text
实现文件
→ 当前行为
→ 它试图解决的问题
→ 依赖的假设
→ 可比较的替代路线
→ 对应测试
→ 能证明与不能证明
```

缺少上游判断时，可以在当前时间重新做诊断、反证和取舍，但必须标为“重构阶段形成”，不能写成当初已发生。

### 4. 决定保留、改造或删除

| 决策 | 适用情况 |
|---|---|
| 保留 | 支持核心判断，有测试或可补验证，风险可控 |
| 改造 | 方向正确但端到端断链、AI 边界错误或无法追溯 |
| 删除/降级 | 只增加页面数量、与非目标冲突或无法在时间内验证 |
| 标为限制 | 当前无法安全修改，但必须在 README 和风险文档披露 |

先修复核心判断、失败场景和证据一致性，再做界面与工程清理。

### 5. 恢复文档

- 用 A/B 级证据填写事实。
- 用 C 级证据填写“当前实现推断”并列待确认。
- 历史会议、历史 AI 对话、成员确认和原始决策不存在时写“无可核验记录”。
- 可以记录当前真实的复盘、AI 反证、代码 Review 和新执行验证，并使用真实时间。
- 不倒填时间，不伪造 Prompt，不把新 Review 写成历史过程。

### 6. 重新验证

至少选择一条主路径和一个失败路径做端到端复测。所有因重构修改的行为必须有回归。测试失败时记录失败、修复和复测三段证据。

## 必须向用户或团队确认的事实

仅在本地无法证明且会改变交付结论时请求确认，例如：

- 题目编号或讲师额外技术端要求；
- 成员姓名、真实分工、会议和个人判断；
- 历史 AI 使用与采纳/拒绝；
- 外部服务密钥、部署地址或不可访问证据；
- 哪些功能代表团队真实选择而不是临时实验。

在得到确认前使用“待确认”，不要编造一个方便的答案。
