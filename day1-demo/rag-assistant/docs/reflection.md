# 复盘反思 — RAG 课程助手

## 核心认知：Spec 驱动 + 测试驱动的 AI 开发流程

今天最大的收获不是 RAG 技术本身，而是**如何用规范流程约束 AI 开发**。

### Spec 驱动开发：先定义"不做什么"

传统开发习惯是"拿到需求直接写代码"。今天学到的第一课是：**没有 Spec，AI 会帮你做过度设计**。

我在 Spec 里写了 5 条非目标（不做 Web UI、不接真实 API、不做向量检索、不支持其他数据源、不做同义词自动扩展）。这 5 条不是摆设——在讨论阶段，AI 确实建议了 embedding 语义搜索、真实 OpenAI API、同义词自动扩展，都被我用"非目标里写了"拒绝了。

**关键体悟**：非目标的价值不在于"我不做这些"，而在于**给 AI 的建议设一个过滤器**。没有非目标，AI 的每个建议都"听起来合理"，你无法拒绝；有了非目标，你可以说"这不在 Spec 范围内"——这是基于设计决策的拒绝，不是基于个人喜好。

### 测试驱动开发：先写测试再写代码

第二课是 TDD。我在写任何实现代码之前，先写了 test_rag.py（13 个用例）。这意味着：

1. **实现有明确的完成标准**：不是"代码能跑"，而是"13 个用例全部通过"
2. **调试有明确的复现路径**：retrieve.py 的分词问题，是通过跑测试用例发现的，不是靠"感觉不对"
3. **重构有信心**：改了 mock server 后，跑一遍测试就知道有没有破坏已有功能

**关键体悟**：测试不是"写完代码验证一下"，而是**定义你要做什么**。questions.json 里的 13 个用例，本质上就是另一种形式的 Spec。

### 流程的价值：每一步都有记录

第三个认知是**可复核交付**的意义。ai-log.md 记录了 14 条决策，test-record.md 记录了 34 个测试结果，git log 有 20 个有意义的 commit。这些记录不是给助教看的——是给我自己看的。

当我在 retrieve.py 的分词上卡了很久时，回看 ai-log 里的"确定检索策略"记录，提醒了我"关键词匹配就够了，不要过度设计"。当 mock server 测试失败时，回看 spec 里的验收标准，帮我判断"是测试期望值有问题还是实现有问题"。

## 遇到的困难

### 困难 1：中文分词粒度（耗时最长）

**事件**：实现 retrieve.py 时，"Day1要交什么？" 无法正确匹配到 faq-02。

**尝试过的方案**：
1. 单字拆分 → 噪声太大，资料外问题无法拒答
2. 整句不拆分 → 无法匹配子串
3. 2-gram 重叠 → 产生垃圾 token

**最终方案**：先按停用词拆分，再按字符类型边界拆分（英文 vs 中文），得到 ["Day1", "提交"]。

**教训**：中文没有天然的词边界，分词策略需要根据匹配目标来设计。这个困难本质上是**Spec 里没有定义清楚"关键词匹配"的具体算法**导致的——design.md 后来补充了分词算法描述。

### 困难 2：评分策略无法区分相关 chunk

**事件**："Day1要交什么？" → faq-01/02/06 分数相同。

**尝试过的方案**：
1. 标题加权 → faq-06 赢了（"Day1"在标题），但用户问的是"交什么"
2. 共现加权 → 仍然平分

**最终方案**：proximity 加权——关键词距离越近加分越多。

**教训**：关键词共现 ≠ 语义相关。proximity 是一个简单有效的启发式方法。

### 困难 3：Mock server 行为与预期不符

**事件**：集成测试 4/13 个用例失败。

**关键决策**：AI 建议"调整测试期望值"，我拒绝了。理由：测试期望值代表 Spec 的验收标准，不应该迁就 mock 而降低标准。选择修复 mock server。

**教训**：mock 不是"随便写写就行"的。测试驱动开发的含义是**测试定义行为**，不是**行为定义测试**。

## 五维能力自评

### 1. 上下文工程：4 分

**证据**：`docs/spec.md` 含 5 条非目标，其中 3 条在讨论阶段拒绝了 AI 的过度建议（embedding 语义搜索、真实 OpenAI API、同义词自动扩展）。验收标准 8 条，每条可测试。`docs/design.md` 的六环节数据流、接口签名、边界场景都是在写代码之前定义好的。

**扣分原因**：Spec 初稿的跨段落验收标准写得太严格（"同时引用"），是 AI review 后才改的。说明 Spec 编写还不够老练。

### 2. 工具链熟练度：4 分

**证据**：`git log` 共 20 个 commit，每个都有有意义的 message（不是 "update" 或 "fix"），按阶段组织（S3 → S6 → Task 1-8）。`.gitignore` 正确配置，`__pycache__` 已从版本控制中移除。

**扣分原因**：中间不小心提交了 `__pycache__`，需要额外 commit 修复。

### 3. 诊断修复：4 分

**证据**：`docs/test-record.md` 包含 34 个测试用例（基础 9 + 自动化 13 + 手动 retrieve 7 + 手动 answer 2 + 端到端 3），覆盖了正常/边界/异常三类输入。mock server 的修复过程遵循了"复现→定位→假设→最小修复→验证"（见 `docs/ai-log.md` 记录 14）。

**扣分原因**：retrieve.py 的分词调试花了较长时间，没有及时停下来和用户讨论。

### 4. 交付完整度：5 分

**证据**：6 类标准文件齐全——`docs/spec.md`、`docs/design.md`、`docs/ai-log.md`、`docs/test-record.md`、`README.md`、`docs/reflection.md`。助教只看文件就能判断：README 能跑通（`python tests/test_basic.py` 和 `python tests/test_rag.py` 全部通过），ai-log 有 14 条决策记录（8 条拒绝、4 条修改），test-record 有 34 个具体用例。

### 5. RAG 理解应用：4 分

**证据**：`docs/design.md` 的 RAG 六环节数据流完整（资料源→切片→检索→Prompt拼接→来源引用→资料外拒答），每环节标注了输入/输出/实现位置。`src/retrieve.py` 实现了切片、同义词映射、停用词过滤、proximity 评分。`src/main.py` 实现了零命中拒答和来源引用输出。`llm-mock/mock_server.py` 实现了资料外拒答（含"混淆类"问题的拒绝模式）。

**扣分原因**：检索算法是关键词匹配 + proximity 启发式，不是真正的语义检索。如果 FAQ 规模增大到 100+，当前策略需要重构（design.md 第 6 节已分析）。

## 改进方向

1. **Spec 编写要更老练**：验收标准应该在初稿就写对，不要等 AI review 才发现太严格
2. **调试时及时停下**：分词调试花了太长时间，应该早点和用户讨论而不是反复试错
3. **检索算法可升级**：proximity 是 MVP 方案，后续可引入 TF-IDF 或 BM25
