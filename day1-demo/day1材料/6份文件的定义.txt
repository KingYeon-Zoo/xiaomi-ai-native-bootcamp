概念：spec.md + design.md —— 定义做什么和怎么做

spec.md 定义目标/非目标/验收标准；design.md 解释架构逻辑和技术决策。没有 Spec，AI 会帮你做过度开发；没有 Design，别人不知道为什么这么写。

✅ 正确做法

• spec.md：目标≤5条，非目标≥3条（封堵AI过度设计），验收标准≥3条且可测试
• design.md：写出为什么选这个方案、数据流怎么走
• 同桌只看 Spec 就能判断你要做什么、不做什么、怎么算做完

❌ 常见错误

• 不写 Spec，拿到需求直接让 AI 写代码
• Spec 写成「做一个RAG系统」——太宽泛，无法验证
• design.md 只写「用了RAG架构」——没说怎么切片、怎么检索、怎么拒答
• 写完代码才补 design.md——变成回忆录而非设计决策

概念：test-record.md —— 怎么证明你做完了

test-record.md 记录每次测试的输入 / 预期输出 / 实际输出。不用跑代码就能判断结果是否正确——这是可复核交付的核心。

✅ 正确做法

• 三栏格式：输入｜预期输出｜实际输出
• 每个函数至少 2 个用例（正常 + 边界）
• 标 ✅ PASS / ❌ FAIL，FAIL 要有说明
• 测试与 Spec 的验收标准一一对应

❌ 常见错误

• 只有代码没有测试记录——说「跑过了」但无法验证
• 测试记录只有「全部通过」四个字——没有具体用例
• 只测正常情况（「abc」），不测边界（空字符串 / 非字符串）
• 先写代码再补测试记录——变成回忆录


概念：ai-log.md —— AI 参与了什么，你做了什么判断

ai-log 记录每次 AI 协作的完整决策链。五字段缺一不可：目的 / 输入 / 建议 / 人工判断 / 验证。「人工判断」是最关键字段——必须写清你采纳 / 修改 / 拒绝了 AI 的什么建议以及为什么。

✅ 正确做法

• 每条记录 5 个字段：目的｜输入｜建议｜人工判断｜验证
• 人工判断写具体理由：【拒绝了双指针方案，改为复用 reverse()，因为代码更短且已有测试覆盖】
• 验证写具体方法：【测试了5个用例，全部通过】
• 不是聊天截图——是结构化的决策记录

❌ 常见错误

• 贴聊天截图代替结构化记录
• 人工判断只写「AI说得对」或为空——评审中视为无效
• 只写 AI 给了什么方案，不写你做了什么判断
• 验证写「代码能跑」——没有具体测试用例


概念：README.md + reflection.md —— 可复现 + 复盘

README 让别人能独立运行；reflection 证明你思考了而不只是执行了。「收获很多」不是复盘——具体事件才是。

✅ 正确做法

• README：安装命令 / 运行命令 / 测试命令 / 环境要求
• README：即使项目简单，也要让同桌不问你就能跑起来
• reflection：写具体事件——「AI建议双指针，我拒绝了，因为可以复用reverse()」
• reflection：写困难和你的决策——不只写成功，也写失败路径

❌ 常见错误

• README 只写项目名和一句话描述——同桌无法复现
• README 假设读者已经知道怎么运行——跳过了关键步骤
• reflection 写「收获很多」或「今天过得很充实」——没有具体事件
• reflection 只写成功的部分——回避困难和不完美的决策
