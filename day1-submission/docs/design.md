# Day 1 技术设计与方案取舍

## 1. 方案比较

### 方案 A：关键词检索 + 本地 Mock LLM

- 适用条件：固定 10 条左右课程 FAQ，重点验证 RAG 数据流和证据链。
- 成本：仅 Python 标准库，无密钥和网络依赖。
- 风险：同义表达和语义召回能力有限。
- 两天可交付性：高，可用自动测试覆盖检索、引用、拒答与边界。

### 方案 B：Embedding + 向量数据库 + 真实模型

- 适用条件：资料规模大、需要语义检索并允许外部依赖。
- 成本：需要模型服务、密钥、依赖安装和索引管理。
- 风险：网络或额度会使评审无法复现，且偏离 Day 1 最小目标。
- 两天可交付性：低，证据链容易被环境问题打断。

### 人工选择

选择方案 A。课程评分关注资料源、切片、检索、Prompt、引用、拒答以及可复核过程；方案 A 能在不引入外部变量的前提下完整验证这些环节。方案 B 记录为后续方向，不纳入本次实现。

## 2. RAG 数据流

```text
course-faq.md
  → 按 ## [faq-XX] 切片
  → 同义词替换、停用词拆分和关键词提取
  → 命中数 + 关键词距离加分
  → 按分数降序取 Top 3
  → 拼接系统指令、参考片段和用户问题
  → 本地 Mock LLM 生成回答
  → CLI 去重来源行并输出 [faq-XX]
```

若问题为空、没有有效关键词或没有任何 FAQ 命中，流程在检索后直接拒答，不调用 Mock LLM。

## 3. 模块与接口

| 模块 | 输入 | 输出 | 职责 |
|---|---|---|---|
| `retrieve._chunk_faq` | FAQ Markdown 字符串 | `{id,title,content}` 列表 | 按 FAQ 标题切片 |
| `retrieve._tokenize` | 用户问题 | 关键词列表 | 同义词替换、停用词处理、字符类型拆分 |
| `retrieve.retrieve` | 问题、FAQ 字符串或 chunks | 最多 3 个带 score 的 chunks | 评分、排序、过滤无命中项 |
| `answer.answer` | 问题、检索 chunks | `{answer,sources}` | Prompt 拼接、Mock 调用、错误返回 |
| `main.main` | CLI 参数 | 标准输出 | 输入边界、加载 FAQ、拒答和来源展示 |

## 4. 失败与异常处理

- Mock 连接失败：`answer()` 捕获异常并返回“调用 LLM 时出错”；不伪装成正常回答。
- 无检索结果：CLI 输出固定拒答且不显示来源。
- 超长问题：在入口截取 200 字，限制单次输入规模。
- Mock 进程遗留：自动测试在 `finally` 中终止，超时后强制结束。
- 端口未就绪：最多等待 10 秒，失败后测试退出非零。

## 5. Bug 修复设计

任务管理器保持原有 `add_task/list_tasks/filter_by_priority` 边界，只在 `add_task()` 入口做两项标准化：标题去空格后必须非空；优先级转为整数或课程别名值。排序与筛选逻辑经纯数字对照用例确认无误，因此不修改。

## 6. 残留风险

- 关键词检索不能理解未出现的同义表达；当前同义词表只有课程已知短语。
- `answer()` 的异常返回仍属于字符串结果，调用者需区分“回答”和“调用错误”。
- 手动运行依赖本机端口 `9876`；自动测试已覆盖启动与关闭，但未处理其他程序长期占用该端口的情况。
