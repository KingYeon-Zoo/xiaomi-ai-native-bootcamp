# 项目三作业要求：Agent 生成代码的重点审查与可信改进

> **适用教案**：《项目三：Agent 生成代码的重点审查与可信改进（45 分钟三维精简版）》
> **满分**：100 分
> **课时**：1 课时，45 分钟
> **唯一提交物**：`agent_review_report.md`

---

## 一、项目目标

本项目评价的不是发现了多少代码坏味道，而是是否能够：

1. 从 Agent Coding 角度完成一次三维审查；
2. 对 Agent 的审查意见进行人工确认；
3. 识别最高优先级问题；
4. 只修改一个问题并控制范围；
5. 使用真实证据判断修改是否值得接受。

评分优先级：

```
人工判断 > 真实代码证据 > 修改范围控制 > 验证可信度 > 报告长度
```

---

## 二、报告结构要求

`agent_review_report.md` 必须包含以下内容：

### 1. 三维审查表

对 Agent 生成的代码（来自项目一/项目二的代码）执行三个维度的审查：

**维度一：需求符合性**

| 项目 | 要求 |
|------|------|
| 检查对象 | 指出具体项目、文件、函数或流程 |
| 任务要求 | 说明代码应该满足什么行为 |
| 实际行为 | 说明代码实际做了什么 |
| 判断依据 | 提供源码、输入输出或运行证据 |

**维度二：变更范围与复杂度**

| 项目 | 要求 |
|------|------|
| 范围定位 | 指出相关文件、函数或实现 |
| 无关内容 | 识别无关代码、重复实现或范围扩大 |
| 复杂度判断 | 识别不必要抽象、依赖或设计 |
| 简化依据 | 说明为什么更简单方案足够 |

**维度三：行为风险与验证证据**

| 项目 | 要求 |
|------|------|
| 风险场景 | 说明可能出错的条件或场景 |
| 行为影响 | 说明对结果、异常或回归的影响 |
| 验证方法 | 给出可执行命令、输入或对比方式 |
| 证据状态 | 正确区分已验证、未验证或证据不足 |

**覆盖要求**：Project 1 和 Project 2 都必须有具体审查证据。不机械套用规则，不能把普通命名、格式和行数问题作为核心风险。

### 2. 候选问题与人工判断（最多 3 条）

每条候选问题需包含：

| 项目 | 要求 |
|------|------|
| 状态选择 | 必须处理 / 重要改进 / 误判 / 待验证 |
| 判断依据 | 使用源码、调用关系、运行或测试证据（不是 Agent 自述） |
| 验证方法 | 说明如何确认问题 |
| 处理决定 | 修改 / 暂缓 / 拒绝 / 继续验证 |

> 不足 3 条不扣分——1-2 条高质量候选优于 3 条虚假或低价值问题。

### 3. 最终问题选择（1 个）

选择一个最高优先级问题进行实际修改，需包含：

| 项目 | 要求 |
|------|------|
| 优先级合理 | 影响需求、范围、复杂度、行为或验证可信度 |
| 根因明确 | 解释问题为什么出现 |
| 人工证据 | 不只复制 Agent 结论 |
| 课堂可处理 | 能在有限范围内完成修改 |

> 如果没有必须阻止代码接受的问题，明确指出"未发现必须处理的问题，选择最重要的改进项"并提供充分证据，不扣分。

### 4. 修改前后代码对比

| 项目 | 要求 |
|------|------|
| 修改前代码 | 能体现问题 |
| 修改后代码 | 能体现改进 |
| 修改说明 | 清楚说明改动内容 |
| 根因对应 | 修改直接解决已确认问题 |

### 5. 三项验证

| 验证项 | 要求 |
|--------|------|
| **V1：目标问题验证** | 修改前问题证据 + 修改后改善证据，前后结果可比较 |
| **V2：核心流程回归** | 运行真实入口或主流程，记录关键结果，说明原行为是否保持 |
| **V3：修改范围检查** | 使用 Git Diff 或等价对比，明确修改文件及无关改动情况 |

验证方式可以是：运行结果、输入输出对比、调用关系对比、代码范围对比、自动化测试或可重复手工验证。**Agent 的自然语言"测试通过"不能作为证据。**

### 6. 书面总结

回答两个问题：

1. 为什么这个问题优先级最高？
2. 哪项证据说明修改后更值得接受？

---

## 三、关键约束

| 约束 | 说明 |
|------|------|
| 最多修改 2 个文件 | 超出需有合理原因 |
| 无新增第三方依赖 | 除非必要且说明 |
| 无无关重构 | 禁止批量格式化、改名、架构升级 |
| 未弱化测试 | 禁止删除、跳过或降低原有验证标准 |
| 不机械套用规则 | 不能把命名、格式、行数问题作为核心风险 |
| Agent 自述 ≠ 证据 | "测试通过"类声明不能作为验证证据 |

---

## 四、常见问题说明

**Q: 没有找到必须处理的问题怎么办？**

如果学生能够证明 Project 1、Project 2 中没有必须阻止接受的问题，并选择一个最重要的改进项进行修改，仍可获得高分。重点是判断是否真实，而不是问题标签是否足够严重。

**Q: 候选问题不足 3 个怎么办？**

候选问题最多 3 个，不是必须凑满。1-2 个高质量候选优于 3 个虚假或低价值问题。

**Q: 问题不是运行 Bug，如何完成 V1？**

可以通过以下方式验证：
- 修改前后调用关系对比
- 修改前后代码范围对比
- 删除重复实现后的行为一致性
- 简化过度抽象后的输入输出一致性
- 补充真实运行命令或测试

**Q: Agent 建议很好，直接采用是否扣分？**

不扣分。关键是是否：核对了问题、理解了优先级、控制了修改范围、提供了真实验证、能够解释修改原因。

---

## 五、优秀作业特征

- 三维审查简短但具体
- 能识别 Agent 时代特有风险
- 不把普通代码风格问题当作最高优先级
- 对 Agent 结论有明确人工证据
- 只修改一个问题
- 修改文件少，没有无关重构
- 验证能够被助教复现
- 能诚实说明未处理风险
- 学生能够独立解释为什么接受这次修改

> **评价重点不是 Agent 给出了多少建议，而是学生是否能够对 Agent 生成代码做出可信的接受或拒绝判断。**
